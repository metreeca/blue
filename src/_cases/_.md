# Blue Limitations

A reply to the limitations reported against Blue, answered against the shape model sketched in `src/_` and measured
rather than reasoned. Each section quotes the report and states where the sketch stands. Four of the seven are closed,
one is already caught at run time, and two turn out to state the model rather than to limit it.

| Limitation                                      | Standing | Notes                                                              |
|-------------------------------------------------|----------|--------------------------------------------------------------------|
| Cycles infer by declaration order               | Closed   | Either end may be declared first, whatever closes the cycle        |
| Captive references project to a bare IRI        | Closed   | A submitted resource is described by `Proposal`, not by `Instance` |
| An unrelated reference target compiles          | Covered  | Caught by `narrowsReference`; statically closeable too             |
| Embedding overrides stay out of reach           | By design| Embedding an inherited reference swaps an IRI for a record         |
| Cardinality is not refinable across arity       | By design| Capping an inherited set swaps an array for a bare value           |
| Re-pointing at the declaring shape fails        | Closed   | A property may name the shape that declares it                   |
| A thunk on the path defeats the override check  | Closed   | Ranges are matched by shape kind, so closures no longer matter   |

## Shape cycles infer by declaration order

> A cycle closed by an `extends` edge infers only when the extending shape is declared before the parent it extends;
> otherwise both ends fail with `TS7023`. […] `Organization.hasUnit` is cut with an explicitly annotated
> `reference((): ResourceShape => …)` thunk for that reason. […] Cut the reference edge, never the `extends` edge.

**Closed.** Either end may be declared first, whatever closes the cycle, so no edge needs cutting and no thunk needs
annotating. `cycle.ts` declares the same cycle both ways round as a regression guard.

Ordering was never inherent to shape cycles. It came of checking overrides where a shape is built, which resolves an
extended shape while the extending one is still being inferred: a cycle running back through that shape has nothing to
resolve to yet. Checking them where the state resolves instead keeps the check and drops the constraint, since a state
is resolved on demand and so never feeds a shape's own inference.

## Captive references project to a bare IRI

> A captive reference accepts either an IRI or the target resource inline […] `Instance<>` admits only the IRI […] so the
> inline form has no type to name. Writing a captive target inline therefore takes a cast.
>
> `Event.image` is where this bites […] so the extracted image credits are dropped.

**Closed**, though not by widening `Instance`. A captive target is supplied on submission and never carried on retrieval,
so the inline form belongs to a value type of its own: unioning it into `Instance` would leave every reader narrowing an
alternative a retrieved resource never holds.

A shape accordingly describes two value types. `Instance` states what a retrieved resource carries, a reference always
as an IRI. `Proposal` states what a submitted one carries, and captive proposals nest, so a captor and the resources it
holds captive travel together, as [keep#4](https://github.com/metreeca/keep/issues/4) asks.

| Member                        | `Instance`  | `Proposal`                  |
|-------------------------------|-------------|-----------------------------|
| plain property                | as declared | as declared                 |
| plain reference               | IRI         | IRI                         |
| `captive` reference           | IRI         | IRI or the target proposal  |
| identifier                    | required    | optional                    |
| `foreign`                     | present     | absent                      |

This cost the reference shape a target to name the inline form, and the property factories a `const` constraints
parameter so that `captive` and `foreign` survive as literals rather than widening to `boolean`. A cycle
closed through a captive edge no longer terminates, since the inline form has to name the target state, but a captive
resource cannot outlive the one holding it and so cannot legitimately close one.

## Reference refinement stops at embedding, arity and cycles

### An unrelated target

> An unrelated target compiles and fails only at run time, as `incompatible resource shape override`.

**Covered**, and the report understates it. `narrowsReference` (`Packages/Blue/src/reference.core.ts:73`) walks the
lineage of the refined target and demands the inherited one among its ancestors, directly or transitively, through any
parent, rejecting a redefined `foreign` or `captive` alongside.

The sketch matches a re-pointed target by shape kind alone, so any reference narrows any other whatever it targets. The
same predicate is expressible over the declared parents, so the check could also stand where the state resolves:

```typescript
type Ancestry<S extends Lazy<ResourceShape>>=
	Eager<S> extends { readonly parents: infer P extends Parents } ? P[number] | Ancestries<P> : never

type Extends<C extends Lazy<ResourceShape>, P extends Lazy<ResourceShape>>=
	[P] extends [C] ? true : [P] extends [Ancestry<C>] ? true : false
```

Either way shapes are matched by structure, so two shapes carrying identical members are indistinguishable and a target
reached through one is accepted for the other.

### Embedding and arity

> Swapping an inherited reference for an embedded resource fails […] so embedding overrides stay out of reach.
>
> Cardinality is refinable within the same arity, but not across it […] capping an inherited set at a single value does
> not.

**By design**, both. An extending shape may tighten what it inherits, never restate it in a form its extended shape
cannot stand in for: code holding the extended state has to accept every extending instance. Embedding an inherited
reference hands a record where an IRI was expected, and capping an inherited set hands a bare value where an array was,
so both are refused whatever else they narrow.

The report reads these as ground the refinement fails to reach. They are the boundary it is meant to hold.

### Cycles and thunks

> Re-pointing a property at the very shape that declares it fails as `circular extends chain`. Refining both ends of a
> pair that point at each other exhausts the stack […]
>
> A thunk on the path defeats the check outright. The lineage is matched by structure, and `reference(() => …)` builds
> a fresh closure on every call […]

**Closed**, both. A property may name the shape that declares it, and a thunk on the path is immaterial: ranges are
matched by shape kind, so no two builds of a shape are ever compared and a fresh closure costs nothing.
